`backend/tests/` — Jest con `--experimental-vm-modules` (ESM nativo, sin transpilar). 190 suites / 1203 tests, todos en verde (verificado localmente el 2026-10-05; el último run de CI verificado fue el #165, 2026-09-21, con 144/763 — ver sección CI abajo), todos contra lógica pura o con Supabase/auth mockeados (`jest.unstable_mockModule`), sin tocar la base real. `package.json` fija `"jest": { "testMatch": ["<rootDir>/tests/**/*.test.js"] }` — Jest solo escanea `tests/`, ningún script suelto en la raíz de `backend/` puede volver a colarse en la suite (ver nota histórica al final de esta sección).

**Organización en subcarpetas (2026-08-14):** los 90 archivos que compartían prefijo de dominio (todo antes del primer punto del nombre, ej. `billing.settleOrder.cogs.test.js` → dominio `billing`) se agruparon en 17 subcarpetas: `admin/`, `auth/`, `billing/`, `clients/`, `dataico/`, `documentNumbering/`, `finance/`, `inventory/`, `inventoryImport/`, `mechanics/`, `providers/`, `quickIntakes/`, `services/`, `subscriptionBilling/`, `telegram/`, `workOrders/`, `workshop/`. Los 17 archivos que eran el único de su dominio (`financialEngine.test.js`, `pricing.test.js`, `installments.test.js`, etc. — la tabla de abajo los referencia por nombre plano) se quedaron sueltos en la raíz de `tests/`, junto con `test.mjs`. No requirió tocar Jest config (el `testMatch` por defecto ya es recursivo). Convención para archivos nuevos: si el dominio ya tiene carpeta, el test nuevo va directo ahí; si va a ser el segundo archivo de un dominio hoy suelto en la raíz, mover también el primero a una carpeta nueva.

## Memoria en Render: diagnóstico

Si llega el correo de Render "exceeded its memory limit" (contexto y límites en environment-and-deployment.md):

1. **Dashboard de Render → Metrics**, vista **"Total"** (MB, no porcentaje). Pasar el mouse sobre la gráfica da el valor exacto por instancia. Referencia: ~120MB = solo Node; ~300-400MB = Chromium abierto; un salto brusco justo antes del reinicio = PDFs.
2. **Logs**: el plan actual **no tiene logs de peticiones HTTP** y la app no registra cada PDF, así que los logs de aplicación solo muestran el reinicio (`Instance ... restarted`), no qué lo causó.
3. **Cruzar la hora con la base** (solo lectura): `cash_flow_ledger.created_at` está en **UTC** (Colombia = UTC-5). Filas `CASH_RECEIPT` sueltas = abonos de cuota (comprobante de pago en PDF); un grupo `INC_GROSS`/`TAX_IVA`/`INV_COGS`/`AR_RECOGNITION` con el mismo `work_order_id` = liquidación (comprobante de venta en PDF). Así se identificó el incidente del 2026-09-27.
4. La CPU casi en cero descarta un pico de tráfico; una memoria que sube de a poco sin PDFs de por medio apuntaría a una fuga en Node.

## Regla de privacidad — no negociable

Instrucción explícita del usuario (2026-07-26): **ninguna alerta puede contener datos reales/sensibles de un taller o de sus clientes** (nombres, cédulas, teléfonos embebidos en texto de error de terceros, montos financieros del cliente, etc.). Como mucho, una alerta puede **identificar de qué taller viene el fallo** vía su nombre, correo y/o teléfono — nunca datos de sus clientes.

Dos mecanismos separados según el origen del error:

- **Errores internos** (Postgres, lógica propia): se pasan por `sanitizeErrorMessage()` antes de entrar al texto del mensaje.
- **Errores de terceros** (Dataico, Meta/WhatsApp): su texto **ni siquiera se sanea** — se **omite por completo**, porque sus mensajes de validación citan el dato exacto que rechazaron (nombre del cliente, NIT, teléfono) en formatos impredecibles que un regex no puede cubrir con confianza. En su lugar, la alerta solo dice qué taller/orden se vio afectado y remite a revisar los logs de Render.

```js
// backend/services/telegramAlerts.service.js
export const sanitizeErrorMessage = (message, maxLen = 300) => {
  let msg = String(message ?? 'Error desconocido');
  msg = msg.split(/\bDETAIL:/i)[0].trim();               // Postgres cita el valor real en el DETAIL de un error de restricción
  msg = msg.replace(/\([\w."]+\)\s*=\s*\([^)]*\)/g, '(...)'); // patrón residual "(columna)=(valor)" fuera del DETAIL
  return msg.slice(0, maxLen) || 'Error desconocido';
};
```

Ejemplo real de por qué hace falta: `duplicate key value violates unique constraint "clients_cedula_key"\nDETAIL: Key (cedula)=(1020304050) already exists.` → sin `sanitizeErrorMessage`, la cédula real de un cliente llegaría al chat de Telegram del equipo. Cubierto por `tests/telegramAlerts.sanitizeErrorMessage.test.js`.

### Flujo de vinculación (QR)

1. El admin abre `/admin/alertas` → un endpoint interno de administración genera un token de un solo uso (10 min) y el QR (`t.me/<bot>?start=<token>`).
2. Al escanear y darle "Iniciar" en Telegram, `POST /api/telegram-alerts/webhook` (público, fail-closed vía `X-Telegram-Bot-Api-Secret-Token` == `TELEGRAM_ALERTS_WEBHOOK_SECRET`) procesa `/start <token>`, valida que no esté usado/expirado, hace `upsert` del `chat_id` en `admin_alert_subscribers` (`onConflict: chat_id`) y marca el token usado.
3. No hay límite de cuántas personas pueden vincularse — cada escaneo genera su propio token y se suma a la lista de suscriptores. Siempre responde 200 (salvo secret inválido), mismo criterio que el bot de clientes ante el reintento agresivo de Telegram.
