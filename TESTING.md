## CI

**GitHub Actions (`.github/workflows/ci-backend.yml`)**: corre esta misma suite en cada push/PR a `main`/`develop`, con Node 22 y pnpm 10.34.5 (mismas versiones que usa el `Dockerfile` de producción — mantenerlas alineadas evita mismatches de lockfile/runtime entre CI y el build real). Requiere los secrets `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `JWT_SECRET` y `ADMIN_JWT_SECRET` configurados en el repo — el resto de integraciones (AWS, WhatsApp, Dataico, Mercado Pago, Bold/Addi, Resend) están mockeadas en los tests y no hacen falta en CI. Nota aparte: `config/resendClient.js` instancia el SDK de Resend de forma perezosa (no al importar el módulo) precisamente porque el SDK lanza una excepción si `RESEND_API_KEY` no está definido — sin ese lazy-init, cualquier suite que importe `server.js` (casi todas) fallaría en CI al no tener esa key configurada.

## Prueba de carga (`backend/loadtest/`, rev. 28)

Separada por completo de Jest — no la corre CI, es manual y bajo demanda. Usa [Artillery](https://www.artillery.io/) contra un taller **desechable**, creado a propósito sin credenciales Dataico en `workshop_config`, para que `isDataicoReady` (`billing.controller.js`) nunca pueda dar `true` sin importar cuántas liquidaciones simule — es el mecanismo de seguridad que permite correr la prueba las veces que haga falta sin riesgo de tocar la DIAN de verdad.

| Archivo | Qué hace |
|:---|:---|
| `loadtest/seed.mjs --target=local\|prod` | Crea el taller desechable vía `POST /api/admin/workshops` (email ya confirmado, sin depender de correo real), firma el Contrato B2B (obligatorio, todo endpoint protegido lo exige salvo `/sign-contract`), siembra 3 mecánicos + 5 ítems de inventario. Guarda el resultado (token, ids) en `.seed-<target>.json` (gitignored) — Artillery lo lee de ahí en vez de crear el taller en cada corrida |
| `loadtest/artillery.yml` | 4 escenarios con peso: Recepción (30%, incl. `request-otp` esperando 404 porque el flujo de Recepción no crea fila en `clients`), Bahía (35%, crear orden → agregar repuesto → liquidar contado), Inventario (15%), Registro público (20%, `public-register` requiere un `intakeId` real, no es alta libre). `environments.prod` corre a la mitad de escala con rampa más gradual que local |
| `loadtest/processor.cjs` | Helpers de Artillery (inyecta el JWT semillado, genera cédula/teléfono/placa aleatorios por iteración). **CommonJS a propósito** (`.cjs`, no `.js` aunque `package.json` tenga `"type":"module"`): el plugin por defecto de Artillery `metrics-by-endpoint` le agrega propiedades al módulo del processor en caliente — un namespace ESM está sellado y esa asignación crasheaba el worker (`processFunc is not a function`) |
| `loadtest/dataico-smoke-test.mjs --confirm` | Un solo disparo manual — **nunca** parte de la corrida masiva de arriba. Login con credenciales de un taller REAL configurado con Dataico, crea una orden mínima, liquida, reporta si vino `cufe`/`pdf_url`. Doble confirmación (`--confirm` + escribir `EMITIR` en la terminal) porque consume un documento real e irreversible (sin nota crédito en el sistema) |
| `loadtest/dataico-efisco-smoke-test.mjs --confirm` | Mismo patrón pero para Caso 2 (EFISCO facturándole a un taller) — llama `POST /admin/accounting/subscription-invoice` directo, sin crear una orden de trabajo |

Corridas reales de rev. 28: local (1080 vusers, 0 fallos, p95 1.5s) y producción a mitad de escala (495 vusers, 0 fallos, p95 2.3s) — ambas contra talleres desechables sin Dataico. Los dos smoke-tests de Dataico (Caso 1 y Caso 2) se corrieron una vez cada uno contra la cuenta real de EFISCO, ambos exitosos (`DIAN_ACEPTADO`, CUFE real) — encontraron y confirmaron el fix de 3 bugs reales que nunca se habían ejercitado contra la API real de Dataico (`sku` faltante en los ítems de Caso 1; `legal_address_line`/`dataico_document_id` leyendo campos que no existen en Caso 2) y una variable de entorno faltante (`DATAICO_ENV=PRODUCCION`) — ver [ARCHITECTURE.md](ARCHITECTURE.md#variables-de-entorno) y [BUSINESS_RULES.md](BUSINESS_RULES.md#contabilidad-admincontabilidad).

Prerrequisitos antes de correr cualquiera de los dos: `WHATSAPP_ENABLED=false` (local y Render) para que los envíos simulados de OTP/comprobantes no toquen la API real de Meta/Telegram; `loadtest/.env.loadtest` y `loadtest/.env.dataico-smoke-test` (gitignored, nunca se pasan credenciales por chat) con las credenciales reales correspondientes.
